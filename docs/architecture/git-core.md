# Git Core and Rewrite Engine

The backend is a Rust library with a small public façade:

- `GitRepository` owns the repository path, Git executable, and per-repository write lock.
- `GitCommand` carries argv values, access mode, optional environment overrides, and optional stdin.
- `GitRunner` invokes Git with `std::process::Command`; it never uses a shell and preserves raw stderr.
- `GitRunner` records the Git version when opened and resolves the repository Git directory lazily on first use; refreshes reuse those immutable values instead of launching identity-only Git processes.
- `GitRunner::run` acquires the repository lock for a standalone write. Multi-command transactions acquire the lock at the `GitRepository` boundary and must execute their writes with `run_unlocked`; a single-command write such as setting Base must not add an outer lock.
- `rewrite` builds immutable Uncommit and Edit message plans from a remote-tracking Base and the first-parent Editable range.
- `materialize` applies either plan through a temporary index, `commit-tree`, and one expected-old-SHA `update-ref`.
- `exclusion` builds and applies repo-local Excluded submodule plans: it validates a HEAD gitlink, configures `ignore = all`, optionally disables recursive submodule commands, and appends a guarded `pre-commit` block without replacing existing hook bytes.
- `switch` builds and applies Quick branch switch plans: tracked changes are captured by `git stash create`, anchored under `refs/githelper/wip/<branch>`, and removed only after the ref is durable; switching never includes untracked files.
- `sync` fetches a remote-tracking Base ref, anchors tracked changes under `refs/githelper/backup/*`, merges Base without changing a local Base branch, and reapplies Saved work. The oplog phase distinguishes Base merge conflicts from Saved work reapply conflicts; interrupted conflicts can be resumed after the user resolves them, while an interrupted fetch can be retried against the same recorded operation.
- `push` plans and applies the rewrite follow-up force-push for the current branch. It derives the configured remote branch, captures the observed remote-tracking SHA, rejects stale plans, and uses an explicit `--force-with-lease=<remote-ref>:<observed-sha>`.
- `recording` writes an in-flight/completed operation entry under `.git/githelper/oplog.json`.
- `list_operations` reads those entries as recovery-panel data, including exact commands, moved refs, snapshots, phases, and a ref-only recovery command for reversible operations. It never changes refs or the worktree.

Edit message preserves trees, merge parents, and original commit metadata; unlike Uncommit, it does not touch the real index.

Excluded submodule configuration is separate from history cleanup. It writes only repo-local config and the local `pre-commit` hook; cleanup of a pointer already present in the Editable range reuses `plan_uncommit` with that gitlink path. A plan exposes the exact config lines, hook guard, and opt-in staging pathspec so a UI can show them before applying.

The rewrite never checks out commits or writes the user’s working tree. Selected paths are reset in the real index after the branch ref moves. The first slice supports ordinary paths and gitlink entries; UI integration and future operations remain separate layers.
Quick branch switch is the exception to the rewrite engine's no-checkout rule: the user explicitly requests checkout movement, so the operation cleans tracked changes only after their Saved work ref exists. Preflight refuses detached HEAD, active Git operations, invalid or missing local target branches, existing Saved work for the source branch, and untracked paths that overlap files on the target. Returning to a branch does not restore automatically; `restore_saved_work` attempts `stash apply --index`, falls back to a plain apply, and deletes the WIP ref only after success. Snapshot, reset, switch, and restore explicitly disable submodule recursion, so the nested checkout SHA, tracked modifications, and untracked files remain in place even when `submodule.recurse=true`; nested dirt is not classified as superproject Saved work.
Sync intentionally writes the superproject checkout because merging Base is the requested operation. Fetch, snapshot, reset, merge, and reapply explicitly disable submodule recursion, so a submodule's checked-out commit, tracked modifications, and untracked files survive Sync. Nested submodule dirt is not treated as superproject Saved work; staged superproject changes remain eligible for the snapshot. Preflight refuses untracked paths that Base would write, while non-conflicting untracked files survive. A fetch-phase retry first verifies that the recorded branch and HEAD are still checked out, then repeats fetch and continues before any tracked work is reset. A Saved work snapshot remains anchored after success so the recovery panel can retain a durable copy; the current core does not yet garbage-collect old backup refs.

The recovery panel is intentionally a read-only boundary. It can show a copy-pasteable `git update-ref` command for reversible records, but the core does not execute that command as an Undo action; restoring refs alone may not restore the worktree.

The desktop shell lives in `src-tauri/` and loads the Vite-built `ui/` surface. `src-tauri/src/commands/` owns the Tauri boundary: it opens a repository transactionally, exposes typed discovery, and delegates all mutations through `prepare_operation` and `apply_operation`. Every Git-backed Tauri command uses the asynchronous command dispatcher so repository scans and writes run on the worker thread pool instead of blocking the window thread. The browser surface honestly reports unavailable desktop access; fixtures are test-only. The shell depends on `git-helper-core` by path so command handlers do not duplicate Git logic.

Operation reviews list every Git command that the selected path may execute. Composite operations such as Quick switch and Sync must show their snapshot, durable-ref, cleanup, movement, and reapply steps instead of collapsing the review to the final `switch` or `merge`. Runtime-only snapshot values use explicit placeholders, and conditional fallback commands are labelled.

Every review command is derived from the plan or the recorded state it describes, never written by hand. `commands/review_commands/` owns those builders: `rewrite` lists the temporary-index sequence (`read-tree`, `update-index` per Base entry with its real mode and object, `write-tree`, `commit-tree`, one expected-old-SHA `update-ref`, and the path-limited `reset --mixed`) because the rewrite engine never runs `git rebase`; `saved_work` uses the recorded `SavedWork` reference and snapshot, and shows that a restore deletes the snapshot after a successful apply. The Tauri boundary is split accordingly: `commands/prepare/` builds reviews, `commands/apply.rs` executes a consumed plan and phrases the outcome, and `commands/actions.rs` holds only the command entry points.

Inspection is a read-only deep module. It uses stable explicit Git formats and returns typed Base refs, changed paths, editable commits, local branches, and gitlinks. A single pending typed plan is held in `AppState`; repository changes, cancellation, stale heads, and stale sync fingerprints invalidate it.

`GitRepository::load_state` is the aggregation boundary for the workbench snapshot. It loads the overview, Saved work, recovery operations, and sync status once, then derives overview counters from those same results. Tauri mutation commands that return this snapshot are consumed directly by the controller so a successful write does not trigger a duplicate repository scan. A failed reviewed mutation is different: the review has already been consumed and a composite operation may have recorded recoverable state, so the controller clears the review and reloads the snapshot before showing the error.
