# Git Core and Rewrite Engine

The backend is a Rust library with a small public façade:

- `GitRepository` owns the repository path, Git executable, and per-repository write lock.
- `GitCommand` carries argv values, access mode, optional environment overrides, and optional stdin.
- `GitRunner` invokes Git with `std::process::Command`; it never uses a shell and preserves raw stderr. `GitError::Command` includes a short argv summary and trimmed stderr in its `Display` text so UI banners are actionable.
- `inspection/fetch` spawns `git fetch --progress` and streams its stderr: `\r`/`\n`-separated `phase: N% (done/total)` fragments become `FetchProgress` events for the desktop layer, while non-progress lines are kept as the error tail. `FetchControl` — an `Arc` cancel flag plus the child handle — lets the desktop `cancel_fetch` command kill the process; a cancelled fetch reports `FetchStatus::Cancelled` instead of a Git error.
- `GitRunner` records the Git version when opened and resolves the repository Git directory lazily on first use; refreshes reuse those immutable values instead of launching identity-only Git processes. Desktop `open_path` additionally probes that the path is a worktree with a `HEAD` before swapping the live session.
- `GitRunner::run` acquires the repository lock for a standalone write. Multi-command transactions acquire the lock at the `GitRepository` boundary and must execute their writes with `run_unlocked`; a single-command write such as setting Base must not add an outer lock.
- `rewrite` builds immutable Uncommit and Edit message plans from a remote-tracking Base and the first-parent Editable range.
- `materialize` applies either rewrite plan through a temporary index, `commit-tree`, and one expected-old-SHA `update-ref`.
- `revert` overwrites selected tracked paths in the index and worktree from HEAD or Base without rewriting history; discovery is the union of porcelain tracked dirt and `Base...HEAD`.
- `exclusion` builds and applies repo-local Excluded submodule plans: it validates a HEAD gitlink, configures `ignore = all`, optionally disables recursive submodule commands, and appends a guarded `pre-commit` block without replacing existing hook bytes.
- `submodule_cleanup` plans and applies composite cleanup for dirty gitlinks: optional Uncommit (reusing `rewrite`) then Revert (restore gitlink to HEAD, `submodule update --force`, nested `checkout --force HEAD`, and `clean -fd`). Discovery is `dirty_submodules`, not `changed_paths` alone.
- `switch` builds and applies Quick branch switch plans: tracked changes are captured by `git stash create`, anchored under `refs/githelper/wip/<branch>`, and removed only after the ref is durable; switching never includes untracked files. With **carry changes**, the snapshot is reapplied on the target branch instead of being stored on the source.
- `sync` fetches a remote-tracking Base ref, anchors tracked changes under `refs/githelper/backup/*`, merges Base without changing a local Base branch, and reapplies Saved work. The oplog phase distinguishes Base merge conflicts from Saved work reapply conflicts; interrupted conflicts can be resumed after the user resolves them, while an interrupted fetch can be retried against the same recorded operation.
- `merge_commit` finishes an in-progress merge by committing a tree built from the three-way merge plus staged conflict resolutions only; unrelated staged work stays out of the commit so `Base…HEAD` cannot gain extra paths when `MERGE_HEAD` is Base.
- `split` builds and applies Split branch plans: it copies the changes of selected paths onto a new branch rooted at the merge base of Base and HEAD, inside a temporary detached worktree, and never touches the source branch.
- `push` covers two distinct remote writes. Publishing is the first push of a branch the remote has never seen: it uses `--force-with-lease=<ref>:`, whose empty expected value requires the ref to be absent, so it can only ever create. Force-pushing is the rewrite follow-up for the current branch.
- `push` plans and applies the rewrite follow-up force-push for the current branch. It derives the configured remote branch, captures the observed remote-tracking SHA, rejects stale plans, and uses an explicit `--force-with-lease=<remote-ref>:<observed-sha>`.
- `cleanup` discovers and deletes branches already contained in Base. Discovery returns the maximal offerable set once, annotated so the UI's toggles filter it without another scan; planning recomputes that set rather than trusting the caller, so the safety exclusions cannot be bypassed through the plan API.
- `recording` writes an in-flight/completed operation entry under `.git/githelper/oplog.json`.
- `list_operations` reads those entries as recovery-panel data, including exact commands, moved refs, snapshots, phases, and a ref-only recovery command for reversible operations. Finishing an operation clears its recorded phase: a phase is an in-flight marker, and a finished record that keeps one reads as still stopped at its last conflict. A recorded previous value that is empty means the ref did not exist before the operation, so its recovery command deletes the ref instead of restoring a former target. It never changes refs or the worktree.

Edit message preserves trees, merge parents, and original commit metadata; unlike Uncommit, it does not touch the real index.

Revert is the opposite trade: it writes the index and worktree for selected tracked paths (`git restore --staged --worktree`) and never moves branch refs. Review alone is the safety surface — there is no Saved work snapshot before the overwrite. Pathspecs use `:(top,literal)` so a repository opened below the Git root still matches root-relative names.

Excluded submodule configuration is separate from history cleanup. It writes only repo-local config and the local `pre-commit` hook; cleanup of a pointer already present in the Editable range is offered on the **Submodules** tab as **Cleanup dirty submodules**, chaining optional Uncommit with Revert. `changed_paths` passes `--ignore-submodules=none` so Uncommit and Split path lists include committed gitlink diffs even when status uses `ignore = all`. A plan exposes the exact config lines, hook guard, and opt-in staging pathspec so a UI can show them before applying.

The rewrite never checks out commits or writes the user’s working tree. Selected paths are reset in the real index after the branch ref moves. The first slice supports ordinary paths and gitlink entries; UI integration and future operations remain separate layers.
Quick branch switch is the exception to the rewrite engine's no-checkout rule: the user explicitly requests checkout movement, so the operation cleans tracked changes only after their Saved work ref exists. Preflight refuses detached HEAD, active Git operations, invalid targets, creating a local that already exists, existing Saved work for the source branch (unless carry changes is enabled), and directory-vs-file untracked prefix overlaps on the target. Same-path untracked overlaps without `merge_untracked` return a typed prepare block with a merge offer; with the flag, overlaps are parked and merged onto the target after checkout (never into source Saved work). Branch discovery lists every non-current local branch and every remote-tracking branch that has no same-named local (so the UI can create a tracking local). Pull after switch (default on) runs `git pull --ff-only` against a same-named remote after checkout and before carry pop; a failed fast-forward pauses with oplog phase `pull-ff-failed` and offers replace (`reset --hard`), merge-pull, or cancel, persisting carry and untracked-merge park refs until resolution. A carry whose pop and plain-pop fallback both fail is rescued onto `refs/githelper/wip/<source-branch>` and dropped from the shared stash stack, because the app lists Saved work from `refs/githelper/wip/*` only and never runs `git stash list` — an entry left on the stack is unreachable from every app surface. The rescue is skipped when that ref already exists. Returning to a branch does not restore automatically; the UI notices Saved work on the current branch (switch outcome follow-up, or a persistent banner on open/refresh) and offers the restore review. `restore_saved_work` attempts `stash apply --index`, falls back to a plain apply only when the failed indexed apply left no unmerged paths, and deletes the WIP ref only after the snapshot is consumed into the tree. A conflicted apply keeps conflict markers and returns a warn-tone success rather than a hard error; the WIP ref is kept when the snapshot was not consumed. When apply hard-refuses because local dirt would be overwritten, current dirt is parked under `refs/githelper/restore-park/*`, the tree is reset, Saved work is applied, then the park is reapplied (after staging) so Git can three-way merge. The **Diff** action previews that restore with `merge-tree` (minimum Git 2.39 for `--merge-base` on trees) without mutating the checkout. Snapshot, reset, switch, and restore explicitly disable submodule recursion, so the nested checkout SHA, tracked modifications, and untracked files remain in place even when `submodule.recurse=true`; nested dirt is not classified as superproject Saved work.
Sync intentionally writes the superproject checkout because merging Base is the requested operation. Fetch, snapshot, reset, merge, and reapply explicitly disable submodule recursion, so a submodule's checked-out commit, tracked modifications, and untracked files survive Sync. Nested submodule dirt is not treated as superproject Saved work; staged superproject changes remain eligible for the snapshot. Preflight refuses untracked paths that Base would write, while non-conflicting untracked files survive. A fetch-phase retry first verifies that the recorded branch and HEAD are still checked out, then repeats fetch and continues before any tracked work is reset. A Saved work snapshot remains anchored after success so the recovery panel can retain a durable copy; the current core does not yet garbage-collect old backup refs. Resuming a `wip-reapply-conflict` deliberately does not reapply the snapshot — the user's in-place resolution would be clobbered — so completion instead verifies that tracked changes exist. A snapshot is only ever written when there were changes to set aside, so an anchored snapshot plus a clean worktree proves nothing was restored; that case finishes with `saved_work_warning` and keeps the ref rather than reporting a clean success.

Split branch is copy-only by design. Move — rewriting the source branch or adding a revert commit to it — is deliberately not implemented, so a Split plan contains no rewrite and the source branch, index, and working tree are untouched. Work happens in a detached worktree under `.git/githelper/worktrees/`, created with submodule recursion disabled and removed on every exit path, so the user's checkout never churns. The commit is produced by `write-tree` plus `commit-tree` rather than `add -A && commit`: staging everything in the temporary worktree would sweep whatever else lives there and would let Git pick the parent implicitly. The branch is created with `update-ref <ref> <commit> ''`, whose empty old value means "must not exist", so a branch created concurrently fails the write instead of being overwritten. Hunk-level splitting is out of scope; selection is by path.

Publishing a split branch is deliberately not a force push. Nothing on the remote is replaced, so the review carries no rewrite warning and no "others must reset" caution — attaching force-push language to a first push would teach the user to ignore it where it matters. The remote is taken from the checked-out branch's `branch.<name>.remote`, then `remote.pushDefault`; with neither set, publishing fails rather than assuming `origin`. An existing remote-tracking ref is refused at planning, and the empty lease still catches a branch pushed by someone else since.

Path selection carries an invariant the caller cannot opt out of: a changed Unity `.meta` file always travels with its asset and an asset always travels with its `.meta`. The planner resolves those companions itself and reports them separately, because a split that lands one without the other produces a branch that is broken on arrival.

Cleanup carries three rules a future change must not undo. **Remote deletions run before local ones** — the inverse of the usual "do the reversible work first", because the local branch *is* the backup for an irreversible server deletion, and a rejected push then fails before anything has been destroyed. **Remote-tracking refs stay out of `refs_before`**: they match the `refs/` prefix `recovery::restore_refs` filters on, so recording one would emit an `update-ref` that recreates a local pointer to a server branch that no longer exists. The two phases therefore write two records — `cleanup-local-branches` reversible with old SHAs, `cleanup-remote-branches` irreversible with an empty `refs_before` so it fails *both* recovery gates — rather than one record whose recovery command would be true but partial. And a **branch checked out in any worktree is never offered**, because `update-ref -d` does not refuse one the way `git branch -d` does and would leave that worktree's HEAD dangling.

Deletion uses plumbing with explicit expectations, not porcelain: `update-ref -d <ref> <expected-sha>` locally (`git branch -d` measures merged-ness against HEAD, not Base) and `push --atomic --force-with-lease=<ref>:<observed-sha>` remotely. The lease is honoured on a delete refspec and is the only guard against removing work pushed since the last fetch; `--atomic` means a lost lease deletes nothing on that remote. A counterpart is resolved from `%(upstream:remotename)`/`%(upstream:remoteref)` or not at all — `switch`'s `same_named_remote` fallback is fine for choosing what to pull and not for choosing what to destroy on a server. Identity comes from `git config --get user.email` **without** `--local`, unlike every other config read here, because that value normally lives in the global file.

The recovery panel is intentionally a read-only boundary. It can show a copy-pasteable `git update-ref` command for reversible records, but the core does not execute that command as an Undo action; restoring refs alone may not restore the worktree.

The desktop shell lives in `src-tauri/` and loads the Vite-built `ui/` surface. `src-tauri/src/commands/` owns the Tauri boundary: it opens a repository transactionally, exposes typed discovery, and delegates all mutations through `prepare_operation` and `apply_operation`. Every Git-backed Tauri command uses the asynchronous command dispatcher so repository scans and writes run on the worker thread pool instead of blocking the window thread. Recent repository paths are an app-level preference in the OS app-data directory (`recent-repositories.json`), never under `.git`; `open_repository` records a path only after `GitRepository::open` succeeds, and a failed open prunes that path while leaving the previous session intact. The browser surface honestly reports unavailable desktop access; fixtures are test-only. The shell depends on `git-helper-core` by path so command handlers do not duplicate Git logic. Window close and the always-on system tray are owned by `src-tauri/src/tray.rs` — see [desktop-shell.md](./desktop-shell.md).

Operation reviews list every Git command that the selected path may execute. Composite operations such as Quick switch and Sync must show their snapshot, durable-ref, cleanup, movement, and reapply steps instead of collapsing the review to the final `switch` or `merge`. Runtime-only snapshot values use explicit placeholders, and conditional fallback commands are labelled.

Every review command is derived from the plan or the recorded state it describes, never written by hand. Split branch is the one operation whose review comes straight from the plan: the core planner already derived the sequence, so `prepare/branch.rs` clones `plan.commands` instead of building a second, drifting copy. `commands/review_commands/` owns the other builders: `rewrite` lists the temporary-index sequence (`read-tree`, `update-index` per Base entry with its real mode and object, `write-tree`, `commit-tree`, one expected-old-SHA `update-ref`, and the path-limited `reset --mixed`) because the rewrite engine never runs `git rebase`; `saved_work` uses the recorded `SavedWork` reference and snapshot, and shows that a restore deletes the snapshot after a successful apply. The Tauri boundary is split accordingly: `commands/prepare/` builds reviews, `commands/apply.rs` executes a consumed plan and phrases the outcome, `commands/diffs.rs` holds the three Inspection diff entry points, and `commands/actions.rs` holds the rest. The `#[tauri::command(async)]` audit in `test/ui-smoke.test.mjs` reads both command files, so a new entry-point file must be added there too.

Inspection is a read-only deep module. It uses stable explicit Git formats and returns typed Base refs, changed paths, editable commits, local branches, gitlinks, and — in two shapes — the branch patch. Base-backed queries resolve the remote-tracking ref before running `A...HEAD`, so a missing Base becomes `InvalidBase` instead of a bare exit-code failure. The patch range is selected by `DiffCompare`: **Head** is `Base...HEAD` (merge base to HEAD, committed only); **Local** is `git diff $(git merge-base Base HEAD)` (merge base to working tree, tracked changes). **Files diff** in Local mode additionally appends untracked paths under `UntrackedFilters` discovery constraints — full bodies for ordinary matching files, incomplete stubs for revealed gitignored / `node_modules` paths so ignore trees cannot dominate the list payload; **Raw diff** and `branch_diff` stay tracked-only so the copyable patch cannot drift. It disables color, external diff/textconv, rename collapsing, relative paths, and config-dependent prefixes so clipboard output is a predictable binary-capable patch.

The two diff shapes share one argv builder in `inspection/diff.rs`, and the structured shape is parsed from the very string the copyable shape returns. That is the point: the two Inspection surfaces cannot acquire different flags, disagree about what changed, or fail differently, because there is only one Git invocation to keep honest. A non-UTF-8 patch therefore fails both, identically.

`inspection/patch/` is a private nested module reached only by `diff.rs`. Two rules there are load-bearing and easy to undo: lines are split on `'\n'` alone, because `str::lines()` also strips a trailing `'\r'` and would silently corrupt every context line of a CRLF file; and a hunk ends when its **declared line counts** are satisfied, never at a sentinel prefix, because a content line can legitimately read `diff --git …` or `@@ …`. Unrecognized header lines are skipped rather than fatal, so a header added by a future Git cannot break the viewer. Paths come from `+++` when present (that operand runs to end of line, so it is unambiguous) and otherwise from the symmetry of the `diff --git` operands; `core.quotepath` octal escapes are accumulated as bytes and decoded once, because Git escapes a non-ASCII name one byte at a time.

`full_file_diff` is the context-expansion query: one file, pathspec-pinned with `:(top,literal)`, at a context wide enough to cover any file. It sets `complete`, which is the contract a viewer relies on — the hunks then hold every line, so nothing is left to fetch and expansion controls must disappear. There is deliberately no total-line-count field: gap sizes inside a file follow from hunk arithmetic, and buying the file length up front would cost one Git process per changed file. `--unified` uses a bounded ten million rather than `INT_MAX`, because xdiff computes a hunk's end as `start + change + context` in `int` *before* clamping it to the record count, so a near-`INT_MAX` context overflows negative and the clamp never fires. Changed paths are read with `--no-relative` because those strings are typed identifiers that planners match on: `diff.relative`, or a repository opened below the Git root, would otherwise reshape them. Operations that turn such a name back into a pathspec must write `:(top,literal)`, since plain `:(literal)` resolves against the current prefix and silently matches nothing. A single pending typed plan is held in `AppState`; repository changes, cancellation, stale heads, and stale sync fingerprints invalidate it.

`GitRepository::load_state` is the aggregation boundary for the workbench snapshot. It loads the overview, Saved work, recovery operations, and sync status once, then derives overview counters from those same results. Tauri mutation commands that return this snapshot are consumed directly by the controller so a successful write does not trigger a duplicate repository scan. A failed reviewed mutation is different: the review has already been consumed and a composite operation may have recorded recoverable state, so the controller clears the review and reloads the snapshot before showing the error.
